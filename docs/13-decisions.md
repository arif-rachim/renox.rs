# 13 — Architecture decision records

Every decision serves density, isolation, and development speed. Decisions changed from v1 are marked so the reasoning can be revisited if conditions change. Status values: `accepted`, `proposed`, `superseded`.

To change a decision: add a new ADR (next number) with status `proposed`, reference the one it supersedes, state the evidence (benchmark, incident, user feedback), and update the old one's status after acceptance. Never edit an accepted ADR's reasoning in place.

## D22 — Render path A is the default (decides D7)
Status: accepted
Date: 2026-10-28
Context: D7 keeps two render paths and lets benchmark B8 choose the default. Path B was built for #42 (`crates/renox-template/src/emit_js`): the same compiled templates as one JavaScript module, byte-equal with path A on the whole fixture set. B8 ran the `shop` list page and its `product_list` fragment through both paths end to end on `renox-worker`, at 100 and 1,000 items. At 100 items (26 KB): path A p50 2.40 ms, path B 3.09 ms; tenant CPU 0.70 ms isolate plus 0.26 ms render pool against 1.48 ms isolate. At 1,000 items (253 KB): 10.9 ms against 15.2 ms; 4.03 + 2.40 ms against 10.84 ms. Under 8 concurrent connections at 1,000 items path B served 1–2 requests per second, because nearly every request ended `RENOX_CPU_LIMIT` (the accounting finding #155, made continuous by path B's longer isolate occupancy). Path A lost about 4 % of requests the same way. Measured on the F1 container, not `node-small` (#158); the ratios are large enough that the re-run is not expected to change the decision.
Decision: Pages and fragments render on path A, in Rust, off the isolate thread, under the render limits of `renox-template`. Path B is not a tenant-facing option. The emitter and its byte-equality test stay in `renox-template` as a prototype, so B8 can be re-run when the inputs change. The rule for when path B applies: never by default. Re-open this decision only with a B8 run that shows path B using less total CPU (isolate plus render pool) than path A for a realistic page. Two changes could do that: data sets well beyond 1,000 items where marshaling dominates (B9), or render-pool saturation on `node-small`.
Consequences: Rendering stays outside the tenant's CPU limit and heap (D7's reason), and tenants get one render semantics and one set of limits (fuel, iterations, output, depth, time). We give up rendering without marshaling; B9 stays the cost to watch. Path A's fragment rendering evaluates the whole page first and costs more than the page itself at 1,000 items (B8 findings), which is to fix on path A. TSX in the isolate (`docs/08-template-engine.md`, "Secondary option") keeps its status: not the default.
Alternatives considered: Path B as the default (more tenant CPU and slower in B8, no fuel equivalent, and a JS reimplementation of every filter to keep byte-equal). Path B per page on opt-in (the B8 numbers give no page where it pays off, and two semantics double the test surface). Dropping the prototype (kept: it is small, tested, and lets the decision be re-measured).
Evidence: [B8 result](../bench/results/2026-10-28-B8-render-path-a-vs-b-renox-worker.md), `crates/renox-template/tests/emit_js.rs`, #42, #155.

## D23 — Internal tenants reach the control API over the public path
Status: accepted
Date: 2026-10-29
Context: The dashboard (#57) is a Renox app (design principle 7, dogfooding) and needs the control API: apps, deployments, activate and rollback, logs, usage, secret names. Tenant `fetch` refuses the control plane by design: the node lists the control plane's addresses in `fetch_blocked_addresses` (`crates/renox-cell/src/worker.rs`, `ExtraBlocked` in `crates/renox-runtime/src/ops/net_policy.rs`), and controlled mode refuses to start with an empty list (#55). The F1 gate (#37) opened #164 to choose between (a) the public control-API hostname over the internet path, with no exemption, and (b) a `ctx.platform` op available only to tenants flagged `internal` in the route message (`docs/contracts/deploy-api.md`, Open item 5). The surfaces differ: the control API serves tenant endpoints (bearer `renox_pat_` tokens and `renox_ses_` sessions, scoped, per tenant, section 2) and node endpoints (`/v1/nodes/*`, `/v1/ingest/*`, bearer `renox_node_` tokens) that hand out route tables, secret bundles, artifacts and certificates. The tenant endpoints are already open to the whole internet, the CLI's and the MCP server's path.
Decision: Option (a). An internal tenant is an ordinary tenant. It reaches the control API at its public hostname (`api.<platform domain>`, the URL `renox login` uses), declared in its manifest's `permissions.network` like any other host, and passes through every rule of `ops.md` section 2 unchanged: allowlist, DNS in Rust, every resolved address against the blocked ranges and `fetch_blocked_addresses`, each redirect hop re-checked. The credential is the signed-in user's own (session or tenant token, forwarded per request) or a tenant token scoped to what the app needs (for example `apps:read`, `logs:read`), held as a tenant secret (#54) and read from `ctx.secrets`. It is never a node token and never a token with reach beyond one tenant. `fetch_blocked_addresses` keeps listing the node's own addresses and the control plane's **node-facing** addresses (where `[control] url` resolves); the public API address is neither listed nor exempt. When both surfaces share one address, the operator puts the node-facing listener on its own address before an internal tenant is deployed. There is no `internal` flag in route entries, no `ctx.platform` op, and no per-node or per-tenant exemption in Rust.
Consequences: Easier: no privileged path exists in the runtime, so a V8 escape or a bug in the dashboard yields only the credentials it holds, the same a stolen CLI token gives; no contract change (route entry, `ops.md`, `ctx.d.ts`); the dashboard exercises the same API, limits and audit as every customer (dogfooding). Harder: the dashboard pays an internet round trip per API call (latency, not cost, while F3 runs one region); the operator must keep two address sets apart and the node's list current when the control plane moves; requests from internal tenants leave from node addresses, so the API must never trust a node address for tenant endpoints (it does not: `control/api/src/auth/ip.ts` feeds the socket address to rate limits, audit rows and new-device mail only). The per-IP buckets of sign-up, login and mail (`control/api/src/auth/accounts.ts`) see the node's address for every dashboard user, so the dashboard must not proxy those flows: the browser signs in against the API directly and the dashboard receives the resulting session (#57). A trusted forwarded-for rule for node addresses would be an exemption and is not added. Given up: a `ctx.platform` shortcut for platform-owned apps; if a later internal app needs data the public API does not expose, the answer is a new public endpoint with a scope, not an op. Follow-ups (outside #164's files): the public edge should not route node endpoints at all (defence in depth over the node-token check), and a controlled worker should refuse to start when `[control] url` resolves to an address tenant `fetch` would allow; `deploy-api.md` Open item 5 closes with a pointer here at the next contract edit.
Alternatives considered: (b) a `ctx.platform` op for tenants flagged `internal`: adds a privileged op to every isolate's surface, makes the route pipeline a source of privilege (a wrong `internal` bit is a cross-tenant breach), and needs coordinated changes of `route_entry`, `ops.md` and `ctx.d.ts`; its gain is latency. A per-node exemption from `fetch_blocked_addresses` for a dedicated internal cell: an exemption by configuration that a mis-assigned tenant inherits, and it opens the node-facing endpoints too.
Evidence: #164, #57, #37 (gate F1 notes), `docs/contracts/deploy-api.md` sections 2 and 7 and Open item 5, `docs/24-threat-model.md` B ("SSRF to metadata, loopback, private ranges"), `crates/renox-runtime/tests/internal_control_api.rs` (a normal tenant gets `RENOX_FETCH_BLOCKED` on the node-facing control plane; the dashboard tenant reaches the public API with a scoped token).

## D24 — An in-house design system for Renoxium's own pages
Status: accepted; visual principles amended by D27 (the "dot matrix" language and one self-hosted font)
Date: 2026-11-01
Context: The dashboard (`control/dashboard`) and the site (`www`) were styled by two small hand-written stylesheets with no shared vocabulary, and the owner found the result too plain. `docs/19-platform-wireframes.md` fixes information architecture, not visual design. Any styling must hold to constraints that already bind these apps: no build step (they are Renox apps, and "no build step, no Node" is the promise to tenants), the CSP every app gets (`default-src 'self'`, so nothing from a CDN and no inline `style` attributes), server-rendered HTML with htmx fragments (D9), and Arabic pages served right to left (#336). Candidates checked on 2026-11-01 against npm and the projects' own notices: Pico CSS fit best on paper but was archived on 2026-10-04 (last release 2.1.1, March 2025); Tailwind and daisyUI need a CSS build, and classes added by htmx fragments can be purged; shadcn/ui is React only; Web Awesome renders in the browser, against D7 and D9; Bootstrap 5.3 and Tabler (built on it) are maintained and support right to left, but are large and look generic; Basecoat and Franken UI are young or slower to release and depend on the Tailwind or UIkit ecosystems. The components the two apps need number about fifteen.
Decision: Renoxium's own pages use `packages/ui/renox-ui.css`, written in house. It is plain CSS: design tokens (`--rx-*`), a base, layout, components and utilities; system font stacks with Latin and Arabic faces; only logical properties; light and dark through `prefers-color-scheme`; nothing loaded from anywhere (`url()`, `@import`). The visual idea comes from the product: a node packed with tenant cells, most idle, a few lit. The lit cell (jade) is the only accent and means running, current or the action to take; the brand mark, the site's hero and live status use it. Cool porcelain ground, blue-black ink, one sans family with monospace only for code, sentence-case labels, radius by rank (cell, control, panel). A first draft (cream paper, serif headlines, vermilion, hairline rules, all-caps labels, monospace captions) was dropped on review because each of those is a common default of generated pages rather than a choice made for Renoxium. Each app copies the file into its `public/` folder unchanged and adds a thin layer of its own after it (`control/dashboard/public/app.css`, `www/public/site.css`). Each app's tests check that the copy equals the source and that the app's stylesheets use no physical direction and load nothing (`packages/ui/lint.ts`).
Consequences: Easier: no dependency to upgrade or to lose; the stylesheet stays small and fits the CSP and the no-build rule; the Arabic pages mirror without overrides; a distinct look. Harder: visual design, accessibility (contrast, focus, motion) and browser quirks are ours to get right, with no upstream fixes; every component is built when first needed; the copies must be refreshed by hand (the tests catch drift). Not decided here: whether modules (`modules/*`) and tenant apps get this stylesheet. Offering it to tenants makes it a compatibility surface (class names and tokens become a contract), so that needs its own decision.
Alternatives considered: Pico CSS (archived, no fixes). Tailwind or daisyUI (a build step for the platform's own apps contradicts the no-build promise; purge risk with htmx). shadcn/ui (React). Web Awesome (client-rendered components; no published CSP stance). Bootstrap 5.3 or Tabler (viable; rejected for size, the generic look, and a third-party dependency that would pass to tenants through modules). Basecoat, Franken UI (young or slower releases; Tailwind or UIkit underneath).
Evidence: `packages/ui/README.md`; `control/dashboard/tests/ui.test.ts`; `www/tests/pages.test.ts` ("design system"); [Pico CSS maintenance notice](https://picocss.com/docs/maintenance).

## D25 — The app edge behind Cloudflare; own TLS and ACME removed; no residency promise
Status: accepted; points 2 and 5 amended by D26 (no `edge.renoxium.app`: the fallback origin is the zone apex)
Date: 2026-11-03
Context: The first production install (#366, `node-small`) served every app name DNS only: the worker terminated TLS itself on 443 (SNI, ALPN, HTTP/2), answered ACME HTTP-01 on port 80, loaded certificates the control API ordered and pushed (`certificate_update`), and limited clients by their socket address, which is why `ops/single-host.md` forbade any reverse proxy in front of it. Measured on that host: visitors far from the node paid 2–3 extra round trips per new connection, the provider's network lost about 25–35 % of packets at the first hop, and the TLS/ACME path needed several stopgaps (#391, #394, #397, #398, #399, #404). Separately, the docs and the site promised that tenant data stays in the UAE, and a controlled worker refused any replica outside `me-central-1` without SSE-KMS (#120), so tenant files could not be replicated to Cloudflare R2 and lived only on the node's disk. The owner decided on 2026-11-03 (epic #421).
Decision:
1. **No residency promise.** Renoxium no longer promises that tenant data stays in the UAE or in any one country. The market focus stays: AED pricing, EN/AR with right to left, local PSPs and BNPL, FTA invoices. The DPA keeps its promise of notice before data moves (`www/pages/legal/dpa.html` section 2) and lists the sub-processors, Cloudflare among them. Sectors where the law requires residency (health, and others to check, `docs/21-uae-gcc-strategy.md` section 10) are not served; there are no health-data tenants. The code rule goes with it: `[replication] allowed_regions` and `sse_kms_key_id` are removed, and tenant files are replicated by Litestream to the R2 bucket `renoxium-replicas` with a token of their own (#417). `ops/terraform` (AWS KMS) goes.
2. **Cloudflare Tunnel is the only way in.** `cloudflared` on the host carries every public name: `api.` and `mcp.renoxium.com` to the control API on loopback as before, and `renoxium.app`, `*.renoxium.app` and the SaaS fallback origin `edge.renoxium.app` to the worker. Ports 80 and 443 are closed in the host firewall; only SSH is open. The origin address is not published.
3. **The worker serves plain HTTP/1.1 to `cloudflared` only.** Its inbound TLS, the certificate store and reload, the port 80 listener with ACME and its redirect, HTTP/2 and the SNI/`Host` check (421 `RENOX_HOST_MISMATCH`) are deleted (#418). Outbound TLS (tenant `fetch`, the control client, S3, OTLP) stays. HSTS and CSP `upgrade-insecure-requests` are sent when the request came through a trusted proxy that says `X-Forwarded-Proto: https`, and the client-event origin check uses `https` for those requests. Cloudflare limits are part of the contract: streams (SSE, log follow, the node stream) send a heartbeat every 15 s, well under Cloudflare's 100 s idle cut (524); a request body above 100 MB is refused at the edge; `text/event-stream` and chunked responses are not buffered by `cloudflared`.
4. **The client address comes from `CF-Connecting-IP`, believed only from a trusted peer** (#414). The worker listens on a unix socket (`listen = "unix:/run/renox-edge/worker.sock"`), which `cloudflared` reaches through a `unix:` origin. The socket file is mode 0660 in group `renox-edge`, and on every connection the worker reads the peer's uid (`SO_PEERCRED`): only a uid listed in `[gateway] trusted_socket_users` (the static `renox-tunnel` user of `cloudflared`) is a trusted peer. Any other local process (a tenant child process, another service) that reaches the socket is served with a local address, and its `CF-Connecting-IP`, `X-Forwarded-*`, `True-Client-IP` and `X-Real-IP` headers are ignored and removed before dispatch. A TCP listener keeps `[gateway] trusted_proxies` (CIDR list, empty by default) for other setups; it is not used in production, because any local process could connect to a loopback port. Per-connection budgets give a trusted peer its own, larger cap (`max_connections_per_trusted_peer`). Nothing a tenant controls takes part in the decision.
5. **Every custom domain is a Cloudflare for SaaS custom hostname** on the `renoxium.app` zone, the platform's own `renoxium.com`, `www.renoxium.com` and `dashboard.renoxium.com` included: they are attached to the platform tenant (migration 0028, #396) through the same `addDomain` path as a customer's domain, and the platform dogfoods it. In the `renoxium.com` zone those three are DNS-only (grey) CNAMEs to `edge.renoxium.app`, the apex by CNAME flattening, so the Orange-to-Orange rules of a proxied customer zone do not apply (to verify during the cut-over, #420). `api.` and `mcp.renoxium.com` stay tunnel hostnames of the control API. The fallback origin is `edge.renoxium.app`, a proxied CNAME to the tunnel. Ownership is Cloudflare's pre-validation TXT only: `_renox-verify`, `verify_token`, the DNS resolver code and `CONTROL_DNS_SERVERS` go. Without `CONTROL_CF_*` settings `addDomain` answers 503 `RENOX_UNAVAILABLE`. The status poll never detaches on one negative or failed answer: misses must be consecutive over a grace period, and an API error counts as unknown (the lesson of #398). Customers' apexes: "use `www`, redirect the apex to `www`"; CNAME flattening works where their DNS provider has it; no A record is offered. Removing `Domain.dns`, `Domain.certificate`, the node certificate endpoint and the `certificate_*` messages is a breaking change of the deploy API (#419); it stays on `/v1` (0.6), because nothing is in production yet and until then breaking changes do not open `/v2`.
6. **Lock-in accepted.** Renoxium depends on one vendor for the edge, custom-domain certificates, DDoS protection and object storage. The origin stays a plain HTTP/1.1 server behind a socket, so another edge can be put in front without changing the worker.
Consequences: Easier: TLS near the visitor and warm connections to the origin; no certificate code, store, key custody or renewal in the platform (the TLS keys leave the key inventory); DDoS and IPv6 at the edge; the host has no open port but SSH and its address stays private; R2 replication of tenant files (no more single-disk loss); budget hosts allowed anywhere. Harder: Cloudflare terminates TLS, so it sees every request and response in clear and is a sub-processor (DPA list, `docs/24-threat-model.md`); an outage at Cloudflare takes every app down; per-hostname cost of Cloudflare for SaaS (the first 100 custom hostnames are included in the plan, then about $0.10 per hostname per month; the owner records the exact numbers from the dashboard before enabling); the edge's limits (100 s idle, 100 MB request body on Free/Pro) bind tenant apps; `renox dev` and tests have no TLS, which they did not have before either. Given up: the "data stays in the UAE" selling point and the in-country guarantee tier; health-data and other residency-bound tenants. Obsoleted: #391, #394, #397, #398 (the rule lives on in the status poll), #399, #404, #415, and the TLS part of #406.
Alternatives considered: Keeping the worker's own TLS and ACME with Cloudflare proxied in front (two TLS stacks to run, certificates still ours, and the stopgaps stay). DNS-only records to the node, the status quo (the measured round trips and loss, and an exposed origin). Tunnel public hostnames for the platform's domains instead of SaaS custom hostnames (no per-hostname cost, but a second routing mechanism and the platform would not run the customer path). A TCP loopback listener with `trusted_proxies = ["127.0.0.1/32", "::1/128"]` (any local process, a tenant child included, could forge `CF-Connecting-IP`; closing that needs Landlock and unit rules on every process, while a socket with a uid check closes it in one place). Keeping the residency promise with a UAE cloud region (2–3× the node cost and no R2).
Evidence: #421 and its comments (owner review and corrections, 2026-11-03), #416, #414, #418, #419, #417, #420; #366 and the `node-small` install; `crates/renox-gateway/tests/client_ip.rs` (the trusted-peer rule, the forged header from another uid); `control/api/tests/domains.test.ts` (custom hostnames through `StubCloudflare`).

## D26 — The zone apex is the Cloudflare for SaaS fallback origin; no `edge` hostname
Status: accepted
Date: 2026-11-03
Context: D25 (points 2 and 5) named a separate hostname, `edge.renoxium.app`, as the Cloudflare for SaaS fallback origin and the CNAME target of every custom domain. It was merged in #422 but never created in DNS: the cut-over of `node-small` had not run. Cloudflare for SaaS needs a fallback origin, which can be any proxied record of the SaaS zone, and the apex `renoxium.app` is already a proxied CNAME to the tunnel (it serves the platform's `security.txt` and the redirect to `renoxium.com`). The owner decided on 2026-11-03 (#424) to drop the extra name.
Decision: The fallback origin and the CNAME target of every custom domain are the zone apex, `renoxium.app` (`CONTROL_CF_FALLBACK_ORIGIN=renoxium.app`). The platform's own `renoxium.com`, `www.renoxium.com` and `dashboard.renoxium.com` are DNS-only CNAMEs to `renoxium.app` (the apex by CNAME flattening). No `edge.renoxium.app` record exists. Without Cloudflare configured, the control API shows the platform domain itself as the CNAME target. This amends D25 points 2 and 5; the rest of D25 stands. The owner verifies during the cut-over that Cloudflare accepts the apex as fallback origin; if it does not, one other name of the zone takes its place and is recorded here.
Consequences: Easier: one record fewer to route through the tunnel and to keep out of tenant use; customers point at a name they already see (`renoxium.app`). Harder: the apex carries two roles (the platform's `security.txt` and redirect for requests with Host `renoxium.app`, and the origin of custom hostnames, which arrive with their own Host), so the worker must keep routing by Host, which it does. Not decided: a per-app CNAME target (`<app>.renoxium.app`, covered by the proxied wildcard), which would make the target self-explaining but ties a customer's DNS to an app name.
Alternatives considered: `edge.renoxium.app` (an extra name with no other job). A per-app target (kept for later; the control API change is small, the contract example changes).
Evidence: #424; #421 and its comments; [Cloudflare for SaaS, getting started](https://developers.cloudflare.com/cloudflare-for-platforms/cloudflare-for-saas/start/getting-started/) (the fallback origin is a proxied record of the zone).

## D27 — renox-ui v2 "dot matrix": the visual language of Renoxium's own pages, and one self-hosted font
Status: proposed
Date: 2026-11-03
Context: D24 set the constraints (no build step, no JavaScript, CSP `default-src 'self'`, server-rendered HTML with htmx, logical properties for Arabic) and a first visual idea: cool porcelain, blue-black ink, jade as a lit cell, one sans family, no web fonts. On the live pages the owner found the dashboard, the landing page and the docs still looked like a prototype (epic #429) and supplied a reference: a modern developer-tool landing page in a warm light style with dot-matrix display type. Only its visual language is taken; no logo, wording, number, illustration or diagram of another company is copied (#426). The constraints of D24 are not in question; its visual principles are.
Decision: `packages/ui/renox-ui.css` becomes v2 with this language: a warm off-white paper with a lighter surface and a sunken tone, and a dark counterpart; near-black ink, a secondary ink and a muted grey, each pair with its grounds at WCAG 2.2 AA; hairlines; coral as the one accent, used sparingly (the icon square of the primary button, a live dot, one highlight per view) and never as body text; green, amber and red for states with a word or glyph. Headlines (`.dot`) and big numbers (`.stat`) are set in a dot-matrix face, uppercase and very large; body text is the system sans at weight 400 with tight tracking on large sizes; monospace is for small pill labels (`.pill`) and code. Diagrams (`.flow`) are thin lines leaving the mark's raised tile (two nested rounded squares, the outer tinted) and ending in dots and pill tags; decorative dot fields (`.dots`) are static text, `aria-hidden`, with a CSS-only pulse that `prefers-reduced-motion` stops. Buttons are pills: the primary one black with white text and a leading coral square holding a dot grid; cards are large rounded surfaces split by hairlines; the top bar floats as a rounded surface. **One font is self-hosted, the only exception to D24's "no web fonts":** Doto (SIL Open Font License 1.1), the Black instance subset to Latin capitals, digits and basic punctuation, served as `woff2` from each app's own `public/` with `font-display: swap`, the licence file beside it, under a budget of 40 KB (1.7 KB today). The dot matrix is the brand's voice (a node is a matrix of cells; a lit cell is a dot), so the face is worth the one file; serving it from the same origin keeps the CSP unchanged, and the lint allows a `url()` only when it is a root-relative path of this origin. Arabic never uses the dot face: under `:lang(ar)` display text falls back to the system Arabic face at a heavier weight. Everything else of D24 stands: no build, no JavaScript in the system, nothing from another origin, logical properties only, light and dark by system setting, one file copied unchanged into both apps with a copy test, and a lint that now also checks contrast (`packages/ui/lint.ts`, `contrastFailures`).
Consequences: Easier: a distinct look that comes from the product rather than from a framework's defaults; one vocabulary (tokens, pills, cards, the diagram) for the site, the docs and the dashboard; contrast failures caught by a test. Harder: a font file to carry and licence (OFL: the licence travels with it, the name is not reserved, a subset is a permitted modified version); Doto draws a period as a small cross, so dot-matrix numbers are whole and dot sentences end in words; the apps' own layers (`www/public/site.css`, `control/dashboard/public/app.css`) are rewritten against the new tokens (#428, #427). Given up: the jade cell as the single accent and the porcelain ground of D24's first look; the site's scripted hero (the landing page is now script-free).
Alternatives considered: Keeping D24's look (judged a prototype by the owner). Loading the face from a font CDN (another origin: breaks `default-src 'self'` and adds a third party on every page). The dot headline as an image or SVG text (not selectable, not read by screen readers in the page's language, not translated). Arabic in a dot face (no such face with Arabic under a free licence; a mismatched fallback reads worse than the system face). A variable font (the whole family is 150 KB; one static weight subset is 1.7 KB).
Evidence: #429, #426 (the owner's direction of 2026-11-03), `packages/ui/README.md`, `packages/ui/demo.html`, `packages/ui/lint.ts` (`contrastFailures`, `loadsAnything`), `control/dashboard/tests/ui.test.ts`, `www/tests/pages.test.ts` ("design system"); the OFL text in `packages/ui/doto-OFL.txt`.

## D28 — The SDK on npm is `@renoxium/sdk`
Status: accepted
Date: 2026-11-03
Context: `README.md`, "Naming", said that `renox` is what a developer types or imports, the packages included, and is not renamed. The SDK (`sdk/`, #376) was to be published to npm as the unscoped `renox`. The owner's first manual publish (#431) was refused by the registry with E403: "Package name too similar to existing packages redux, detox". npm's typosquatting rule blocks the name for anyone, so no account or setting fixes it. The owner had created the npm organization `renoxium` for the team access of #376.
Decision: The SDK is the scoped package `@renoxium/sdk`, owned by the `renoxium` npm organization. Tenant code, modules, examples, templates and docs import `@renoxium/sdk`, and the subpaths `@renoxium/sdk/kysely`, `@renoxium/sdk/drizzle`, `@renoxium/sdk/fakes` and `@renoxium/sdk/test`. `renox new` writes `"@renoxium/sdk": "^<cli version>"`. Workspace packages depend on `"@renoxium/sdk": "workspace:*"`. `renox build` resolves `@renoxium/sdk` and its subpaths from the app, then from the SDK next to the CLI, as it did for `renox`. Everything else keeps the name `renox`: the CLI binary and its commands, `renox.toml`, `renox.lock`, the `renox:modules` specifier, the `RENOX_*` codes and variables, the crates, the reserved module name `renox`.
Consequences: Easier: the package publishes; the scope groups future packages (`@renoxium/cli` as a thin npm wrapper around the binaries, if wanted) under one organization with team access, and nobody can squat a name next to it. Harder: an import line is longer than `from "renox"`, and the import name (`@renoxium/sdk`) differs from the CLI name (`renox`), so the naming rule now has one exception. Nothing was ever published as `renox`, so no user has to migrate.
Alternatives considered: `@renox-dev/renox` (npm's suggestion; a personal scope, not the organization). `@renoxium/renox` (keeps the word but reads twice). `@renoxium/cli` (the package is the SDK; the CLI ships as binaries, `docs/12-developer-experience.md`, "Installing the CLI"). A dispute with npm over `renox` (no basis: the rule is about similarity, not ownership).
Evidence: #431; #376; the E403 of the first publish, 2026-11-03.

## D29 — The whole repository is open source under Apache-2.0
Status: accepted
Date: 2026-11-05
Context: `docs/15-roadmap.md` left the data-plane licence open ("open source for contributors and trust, or closed to protect the hosting business", to decide before F7) and `README.md` said "Not yet decided". The repository had no `LICENSE` file while the code of F0 to F7 was already public on GitHub, and `sdk/package.json` carried `"license": "MIT"`, published with `@renoxium/sdk` 0.1.0 to 0.1.3 (#431 to #467), so one part of the code already had a public licence that nothing had decided. The crates declared none. The owner decided on 2026-11-05 (#469).
Decision: Every file of this repository is licensed under the Apache License 2.0 (`LICENSE` at the root, the verbatim text): the data plane (`crates/`), the control plane (`control/`), the CLI, the SDK, `packages/`, the modules, the examples, the site, `ops/`, `bench/` and the documentation. `cli/package.json`, `sdk/package.json` and every crate (`[workspace.package] license`) say so. The one exception is history: `@renoxium/sdk` 0.1.0 to 0.1.3 were published under MIT and a published npm version cannot change, so those versions stay MIT; 0.1.4 and later are Apache-2.0 (`CHANGELOG.md`). The business is the hosting (`docs/01-business.md`): what the company sells is running tenants densely, safely and cheaply with the modules, the dashboard, the billing and the operations around them, not the right to read or run the code. No contributor licence agreement is required beyond what Apache-2.0 section 5 says about contributions.
Consequences: Easier: contributors and agencies can read, run and fix the platform, which is the trust argument of `docs/01` for a hosting business that stores customer data; the express patent grant of Apache-2.0 protects users of the data plane against the project and its contributors; the licence is compatible with every dependency `deny.toml` allows; a tenant can audit the runtime limits and the authorizer it relies on. Harder: a competitor may run the same code; the protection of the business is the operations, the modules' upkeep, the registry and the product, which is what D1 to D28 already assume. Given up: a proprietary data plane as a moat (never built on; the code was public since F0).
Alternatives considered: MIT for everything (shorter, no patent clause; the SDK would not need an exception, but the data plane is where a patent grant matters). Closed data plane with open SDK and CLI (two licences, a boundary to police in every PR, and the trust argument lost for the part that holds customer data). AGPL or a source-available licence (deters the agencies and the module publishers `docs/21` counts on; the business does not depend on exclusivity of the code).
Evidence: #469; `LICENSE`; the owner's decision of 2026-11-05; `npm view @renoxium/sdk@0.1.3 license` (MIT) against `sdk/package.json` on `main` after this ADR (Apache-2.0).

## D30 — The CLI on npm is a Bun package, `@renoxium/cli`, with `bun create renox`
Status: proposed
Date: 2026-11-06
Context: The CLI ships only as standalone binaries (`bun build --compile`, `release-cli.yml`) and through `curl … | sh` (`cli/scripts/install.sh`). Developers who live in npm or Bun expect `bun add -g`, `bunx` or `bun create` to work, and #440 asked for `@renoxium/cli` on npm. #440 as first written followed the esbuild and Biome pattern: one launcher package plus `@renoxium/cli-<os>-<arch>` packages, each carrying the compiled binary of the GitHub release. The owner put #440 on hold on 2026-11-04 for this ADR: "Bun package plus `bun create renox` instead of per-platform binaries". Measured on `main` at `e02ffc3` (2026-11-06):
- The compiled `renox` is 90–110 MB per platform (`cli-v0.1.3`), almost all of it the Bun runtime the binary embeds.
- `bun build --target=bun --minify cli/src/main.ts` is a single 0.83 MB file (0.28 MB gzipped). Run with `bun`, it prints `renox 0.1.3 (renox-worker 0.3.0)` and creates an app with `renox new demo --template hello`.
- The official modules that `cli/scripts/compile.ts` embeds are 1.2 MB (0.34 MB gzipped).
- `renox dev` and `renox test` run the app's tests and tooling with Bun, so every user who gets past `renox new` needs Bun already (`docs/12-developer-experience.md`, "Installing the CLI").
- `create-renox` and `@renoxium/cli` were unclaimed on npm on 2026-11-06.

Decision: The CLI is published to npm as **one** package, `@renoxium/cli`, at the version of the `cli-v<version>` tag:
- **Contents.** `bin/renox.js`, the CLI bundled for Bun (`bun build --target=bun`), with the same embedded modules and test harness as the compiled binary. `cli/scripts/compile.ts` gains a bundle mode that writes it, so both artifacts come from one embedding step.
- **Running it.** The file starts with `#!/usr/bin/env bun`, and `package.json` declares `"bin": { "renox": "bin/renox.js" }` and `"engines": { "bun": ">=1.4" }`. `bun add -g @renoxium/cli`, `bunx @renoxium/cli <command>` and `npm install -g @renoxium/cli` (with Bun on `PATH`) give the same `renox` commands and the same `renox --version` as the binary of that tag.
- **Install scripts.** There are none, so `--ignore-scripts` installs work.
- **`create-renox`.** A second package, so that `bun create renox <app>` (and `npm create renox`) work. It runs `renox new <app>` from the `@renoxium/cli` of the same version, passing `--template` through. If npm refuses the unscoped name (as it refused `renox`, D28), the fallback is `@renoxium/create`, which `bun create @renoxium <app>` resolves; the ADR then records which one was used.
- **The worker** is not in either package. `renox dev`, `renox test` and the template transpile download the pinned `renox-worker` on first use into `~/.renox/bin` and check its sha256 against `PINNED_WORKER` before running it, as the compiled CLI does with the worker beside it. The search order is `RENOX_WORKER_PATH`, beside the CLI, then the cache. The download prints one line with its size. Offline, the command stops with `RENOX_CLI_WORKER_UNVERIFIED`-style guidance and the manual download line.
- **Publishing.** `release-cli.yml` publishes both packages on the `cli-v*` tag with `npm publish --provenance` through trusted publishing (no token), and skips versions that npm already has, as `release-sdk.yml` does for `@renoxium/sdk`.
- **The binaries stay.** The standalone binaries and `install.sh` remain the way to install without Bun, and the sigstore-verified path; nothing about them changes.

Consequences:
- **Easier:** `bun create renox myapp` is one line for the audience the platform targets. An install is about 1 MB instead of about 100 MB, and there is one package to publish and to give a Trusted Publisher instead of five. A Windows user with Bun gets every command that needs no worker without waiting for a native `renox.exe` (#441). The npm package is built from the same source and embedding step as the binary.
- **Harder:** the npm package needs Bun ≥ 1.4 on the machine; `npm install -g` without Bun gives a clear "bun: not found" from the shebang, so the docs say "install Bun first". The npm route is verified by npm provenance, the binaries by sha256 and sigstore; the docs must say which checks which.
- **Given up:** byte-identity between the npm package and the GitHub release binary, which #440 required. The package's JavaScript file is checked by its own provenance instead.

Alternatives considered:
- **Per-platform packages of the compiled binary** (#440 as written; the esbuild and Biome pattern). It works without Bun, but costs about 100 MB per install, five packages and five Trusted Publishers, and a Windows package only once #441 lands.
- **Publishing `cli/src` unbundled.** It would need the workspace package `@renox/artifact-validate` published too, plus the JSON schemas from `docs/contracts/` and the modules at run time from the package directory. The bundle carries all of them already.
- **`npm create` only, without a global CLI.** It leaves `renox dev` and `renox deploy` without an install path.

Evidence: #440 and the owner's comment of 2026-11-04; the sizes above (`bun build --target=bun`, `cli-v0.1.3` release assets); `npm view create-renox` and `npm view @renoxium/cli` returning 404 on 2026-11-06.
