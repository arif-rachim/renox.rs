# 13 — Architecture decision records

Every decision serves density, isolation, and development speed. Decisions changed from v1 are marked so the reasoning can be revisited if conditions change. Status values: `accepted`, `proposed`, `superseded`.

To change a decision: add a new ADR (next number) with status `proposed`, reference the one it supersedes, state the evidence (benchmark, incident, user feedback), and update the old one's status after acceptance. Never edit an accepted ADR's reasoning in place.

## D22 — Render path A is the default (decides D7)
Status: accepted
Date: 2026-10-28
Context: D7 keeps two render paths and lets benchmark B8 choose the default. Path B was built for #42 (`crates/renox-template/src/emit_js`): the same compiled templates as one JavaScript module, byte-equal with path A on the whole fixture set. B8 ran the `shop` list page and its `product_list` fragment through both paths end to end on `renox-worker`, at 100 and 1,000 items. At 100 items (26 KB): path A p50 2.40 ms, path B 3.09 ms; tenant CPU 0.70 ms isolate plus 0.26 ms render pool against 1.48 ms isolate. At 1,000 items (253 KB): 10.9 ms against 15.2 ms; 4.03 + 2.40 ms against 10.84 ms. Under 8 concurrent connections at 1,000 items path B served 1–2 requests per second, because nearly every request ended `RENOX_CPU_LIMIT` (the accounting finding #155, made continuous by path B's longer isolate occupancy). Path A lost about 4 % of requests the same way. Measured on the F1 container, not `node-small` (#158); the ratios are large enough that the re-run is not expected to change the decision.
Decision: Pages and fragments render on path A, in Rust, off the isolate thread, under the render limits of `renox-template`. Path B is not a tenant-facing option. The emitter and its byte-equality test stay in `renox-template` as a prototype, so B8 can be re-run when the inputs change. The rule for when path B applies: never by default. Re-open this decision only with a B8 run that shows path B using less total CPU (isolate plus render pool) than path A for a realistic page. Two changes could do that: data sets well beyond 1,000 items where marshaling dominates (B9), or render-pool saturation on `node-small`.
Consequences: Rendering stays outside the tenant's CPU limit and heap (D7's reason), and tenants get one render semantics and one set of limits (fuel, iterations, output, depth, time). We give up rendering without marshaling; B9 stays the cost to watch. Path A's fragment rendering evaluates the whole page first and costs more than the page itself at 1,000 items (B8 findings), which is to fix on path A. TSX in the isolate (`docs/08-template-engine.md`, "Secondary option") keeps its status: not the default.
Alternatives considered: Path B as the default (more tenant CPU and slower in B8, no fuel equivalent, and a JS reimplementation of every filter to keep byte-equal). Path B per page on opt-in (the B8 numbers give no page where it pays off, and two semantics double the test surface). Dropping the prototype (kept: it is small, tested, and lets the decision be re-measured).
Evidence: [B8 result](../bench/results/2026-10-28-B8-render-path-a-vs-b-renox-worker.md), `crates/renox-template/tests/emit_js.rs`, #42, #155.

## D23 — Internal tenants reach the control API over the public path
Status: accepted
Date: 2026-10-29
Context: The dashboard (#57) is a Renox app (design principle 7, dogfooding) and needs the control API: apps, deployments, activate and rollback, logs, usage, secret names. Tenant `fetch` refuses the control plane by design: the node lists the control plane's addresses in `fetch_blocked_addresses` (`crates/renox-cell/src/worker.rs`, `ExtraBlocked` in `crates/renox-runtime/src/ops/net_policy.rs`), and controlled mode refuses to start with an empty list (#55). The F1 gate (#37) opened #164 to choose between (a) the public control-API hostname over the internet path, with no exemption, and (b) a `ctx.platform` op available only to tenants flagged `internal` in the route message (`docs/contracts/deploy-api.md`, Open item 5). The surfaces differ: the control API serves tenant endpoints (bearer `renox_pat_` tokens and `renox_ses_` sessions, scoped, per tenant, section 2) and node endpoints (`/v1/nodes/*`, `/v1/ingest/*`, bearer `renox_node_` tokens) that hand out route tables, secret bundles, artifacts and certificates. The tenant endpoints are already open to the whole internet, the CLI's and the MCP server's path.
Decision: Option (a). An internal tenant is an ordinary tenant. It reaches the control API at its public hostname (`api.<platform domain>`, the URL `renox login` uses), declared in its manifest's `permissions.network` like any other host, and passes through every rule of `ops.md` section 2 unchanged: allowlist, DNS in Rust, every resolved address against the blocked ranges and `fetch_blocked_addresses`, each redirect hop re-checked. The credential is the signed-in user's own (session or tenant token, forwarded per request) or a tenant token scoped to what the app needs (for example `apps:read`, `logs:read`), held as a tenant secret (#54) and read from `ctx.secrets`. It is never a node token and never a token with reach beyond one tenant. `fetch_blocked_addresses` keeps listing the node's own addresses and the control plane's **node-facing** addresses (where `[control] url` resolves); the public API address is neither listed nor exempt. When both surfaces share one address, the operator puts the node-facing listener on its own address before an internal tenant is deployed. There is no `internal` flag in route entries, no `ctx.platform` op, and no per-node or per-tenant exemption in Rust.
Consequences: Easier: no privileged path exists in the runtime, so a V8 escape or a bug in the dashboard yields only the credentials it holds, the same a stolen CLI token gives; no contract change (route entry, `ops.md`, `ctx.d.ts`); the dashboard exercises the same API, limits and audit as every customer (dogfooding). Harder: the dashboard pays an internet round trip per API call (latency, not cost, while F3 runs one region); the operator must keep two address sets apart and the node's list current when the control plane moves; requests from internal tenants leave from node addresses, so the API must never trust a node address for tenant endpoints (it does not: `control/api/src/auth/ip.ts` feeds the socket address to rate limits, audit rows and new-device mail only). The per-IP buckets of sign-up, login and mail (`control/api/src/auth/accounts.ts`) see the node's address for every dashboard user, so the dashboard must not proxy those flows: the browser signs in against the API directly and the dashboard receives the resulting session (#57). A trusted forwarded-for rule for node addresses would be an exemption and is not added. Given up: a `ctx.platform` shortcut for platform-owned apps; if a later internal app needs data the public API does not expose, the answer is a new public endpoint with a scope, not an op. Follow-ups (outside #164's files): the public edge should not route node endpoints at all (defence in depth over the node-token check), and a controlled worker should refuse to start when `[control] url` resolves to an address tenant `fetch` would allow; `deploy-api.md` Open item 5 closes with a pointer here at the next contract edit.
Alternatives considered: (b) a `ctx.platform` op for tenants flagged `internal`: adds a privileged op to every isolate's surface, makes the route pipeline a source of privilege (a wrong `internal` bit is a cross-tenant breach), and needs coordinated changes of `route_entry`, `ops.md` and `ctx.d.ts`; its gain is latency. A per-node exemption from `fetch_blocked_addresses` for a dedicated internal cell: an exemption by configuration that a mis-assigned tenant inherits, and it opens the node-facing endpoints too.
Evidence: #164, #57, #37 (gate F1 notes), `docs/contracts/deploy-api.md` sections 2 and 7 and Open item 5, `docs/24-threat-model.md` B ("SSRF to metadata, loopback, private ranges"), `crates/renox-runtime/tests/internal_control_api.rs` (a normal tenant gets `RENOX_FETCH_BLOCKED` on the node-facing control plane; the dashboard tenant reaches the public API with a scoped token).
