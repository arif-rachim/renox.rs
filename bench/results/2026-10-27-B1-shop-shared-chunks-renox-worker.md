## Findings (#143)

- **What changed.** `renox build` now bundles all function modules in one `Bun.build` with code splitting: code shared by several modules (zod, `lib/http.ts`) is emitted once under `code/chunks/`, and the source maps are written outside the artifact (`<out>/../sourcemaps/<hash>/`). The artifact stays `esm-dir`; no runtime change was needed, since the loader already resolves relative imports inside `code/` and `deno_core` evaluates each module once per isolate.
- **Artifact size.** `code/` of `shop` went from ≈ 4.1 MB (five self-contained modules, inline source maps; `checkout.js` alone 3.2 MB) to 0.77 MB: `checkout.js` 584 KB (Stripe), the zod chunk 167 KB, the rest under 16 KB each.
- **Where the memory went.** V8 heap per `shop` isolate fell from 13.9 MB to 7.3 MB: the inline source maps were module source text held by V8 (≈ 1.9 MB of map JSON today, more before since each module carried its own copy of zod and its map, base64-encoded), and zod was evaluated twice. RSS outside the heap fell by about 5 MB too (less code space and fewer compiled functions).
- **What remains above `hello`** (11.1 − 7.4 = 3.7 MB): the Stripe SDK (evaluated at isolate creation because `checkout.ts` imports it at top level) and zod. Further levers, not in this issue: lazy evaluation of route modules not needed by the first request, and the V8 code cache in eszip (#30's eszip step).
- **Not eszip.** The gate text (#37) names eszip; the CLI still has no eszip step. The shared-chunk `esm-dir` layout gives the same "each dependency evaluated once" property, which is what the gate condition is about. This run measures the format `renox build` produces today.
- The run also included the batch's lazy reader connections in `renox-data` (#145): for `shop`'s single `GET /api/products` request one reader is opened instead of two, a few hundred KB at most per tenant.
