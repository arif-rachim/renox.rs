# B1 — What the per-module `ctx` facades cost in V8 heap (#642, task 1) — 2026-11-09

Hardware: dev-laptop (session container: Intel(R) Xeon(R) Processor @ 2.30GHz, 4 vCPU, 16 GB RAM, Linux 6.18.44-fc-v310), rustc 1.99.1, `main` at b866c13, release profile (`CARGO_PROFILE_RELEASE_DEBUG=0`).

Scope: task 1 of #642 only, the measurement. `crates/renox-runtime/src/js/bootstrap.js` is unchanged. Tasks 2 to 4 wait for #633, which changes that file, and are to be measured against it.

**Provisional (D31).** Measured in a cloud session container, not on `node-small`. These are V8 heap sizes (`used_heap_size`), which do not depend on the host. They are relative numbers, never a gate.

## Result

| What | Bytes per module | MB per module | Built when |
| --- | --- | --- | --- |
| The `ctx` facade (`ctxOf(m)` → `moduleFields(m)`), retained | **≈ 3.5 KB** (3,553–3,679 B, 5 sets of 3 runs) | **0.0034** | per request, only for the modules that request touches; garbage once the request ends |
| Creation, module registered with no code (`harden`'s frozen info and secrets, `buildProxies`, `register`) | ≈ 3.2–4.1 KB | 0.003–0.004 | once per isolate |
| Creation, module with a 4-service `services.js` (the above plus evaluating that code) | ≈ 9.8 KB | 0.0096 | once per isolate |

**Both are far under task 2's threshold of 0.05 MB per module.** At 12 modules, a request that calls into all of them builds 0.041 MB of facades; one that touches only `app` (like `GET /api/products`) builds one.

**The premise of task 2 does not hold at `main`:** no per-module `ctx` facade is built at isolate creation. `newRequestState(base).ctxOf(m)` (`bootstrap.js`, "The per-request module state") already builds a module's frozen ctx on first use within a request and caches it for that request. Every dispatch path (`dispatch`, `deliver`, `invoke`, services, hooks, events, jobs, tools) goes through it. What is per module at creation is the frozen module info, its secrets, one service-proxy object (a closure per service) and the `register` entries: ≈ 3 KB.

**Recommendation for task 2:** skip it. Making facades lazier would save at most ≈ 3.5 KB per module, and only per request, not per isolate. The V8 heap share of #344 (+0.30 MB for six modules, ≈ 50 KB per module) is the evaluation of the modules' own code, which a 4-service stub barely shows (≈ 6.6 KB above registration). That is #640 (lazy evaluation of module code). The malloc side of #340 is #641.

## Method

Test: `crates/renox-runtime/tests/ctx_facade_heap.rs` (ignored by default, prints the numbers):

```sh
CARGO_PROFILE_RELEASE_DEBUG=0 cargo test --release --locked -p renox-runtime \
  --test ctx_facade_heap -- --ignored --nocapture --test-threads=1
```

The artifacts have N modules `m01`..`m12`, each `shared`, with a three-key `config` and (in the "with code" variant) a `services.js` exporting `keep`, `drop`, `info` and `ping`. The app's one route calls `keep` or `drop` on every module with `?op=`.

1. **Creation.** For every N from 0 to 12, one warm-up isolate fills the code cache. Then 7 isolates are created, each in its own tenant, and the median `CreateStats::used_heap_bytes` is taken. This is the same `used_heap_size` the meter's `peak_heap_bytes` reads, taken right after creation without a forced GC. Per module = the median of the 12 steps N → N + 1.
2. **Facade.** Two isolates of the 12-module artifact each serve 200 requests that call one service on every module. Each call builds that module's ctx. One isolate's services push the ctx they receive into a module global (`keep`). The other's drop it (`drop`). Then both serve one identical `?op=none` request. The difference between the two `peak_heap_bytes`, divided by 200 × 12, is the retained size of one facade with its members (`db`, `fetch`, `log`, `config`, `hooks`, `events`, `jobs`, `storage`, `ai`, `pdf`, `render`, `authz`, `realtime`). `secrets`, `services` and `password` are shared objects and are not counted. 3 such pairs are run, and the median is taken.

`--inspect` and `v8::HeapProfiler` are not reachable from `crates/renox-runtime/tests/`: the isolate lives on its own thread, and `IsolateHandle` exposes only V8's thread-safe handle. A heap snapshot would need a crate change, which was out of scope here. The two counts above use only what the crate already exposes.

**Retained per facade (KB), runs of 3:**
- 3.43, 3.30, 3.56;
- 3.61, 3.53, 3.59;
- 3.47, 3.50, 3.43;
- and two more sets whose medians are 3.50 and 3.49.

**The 0.7 MB step.** Both variants have one jump of ≈ 0.72 MB. It lands at a module count that moves between runs: 8, 9 or 10 with code, and 10 or 11 without. It is sometimes absent at one N and present at the N below, for example 10: 4379.7 against 9: 5071.1 in one run. So it is a heap-growth step of V8 (a new page, or a scavenge happening or not before the read), not a per-module cost. It is why "12 − 0" (863 KB with code, 778 KB without, ≈ 70 KB per module) overstates the per-module figure. It is real heap at the moment of the read, though, and an isolate with 12 modules sits above it in every run. What triggers it was not traced here. A post-GC read, which needs a crate hook, would tell whether it is live memory.
